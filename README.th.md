# AI-Enhanced Attacks on Cloud Infrastructure

**การโจมตีโครงสร้างพื้นฐานคลาวด์ที่เสริมด้วย AI**

*[English](README.md) · ภาษาไทย*

งานทบทวนวรรณกรรมและข้อเสนอโครงการวิจัย ว่าด้วย AI กำลังเปลี่ยน **ความเร็ว** และ **พื้นผิวการโจมตีด้านตัวตน (identity)** ของสภาพแวดล้อมคลาวด์อย่างไร พร้อมการทดลองแบบมีกลุ่มควบคุมที่ออกแบบมาเพื่อวัดผลกระทบเฉพาะจุดหนึ่งของการเปลี่ยนแปลงนั้น

**สถานะ:** ทบทวนวรรณกรรมเสร็จสิ้น · นำเสนอที่ ม.หอการค้าไทย สิงหาคม 2569 · **ยังไม่ได้ดำเนินการทดลอง**

**ผู้จัดทำ:** จารุเดช ทองคุ้ม — วิทยาการคอมพิวเตอร์ มหาวิทยาลัยหอการค้าไทย

## กรณีศึกษา — UNC6426

Google Cloud บันทึกการบุกรุกครั้งหนึ่งที่บีบอัดข้อโต้แย้งทั้งหมดไว้ใน **เวลาไม่ถึง 72 ชั่วโมง** ทุกขั้นตอนด้านล่างอ้างอิงหรือถอดความจากรายงานโดยตรง

```
วันที่ 1   แพ็กเกจ Nx บน npm ถูกฝังโค้ดอันตราย → นักพัฒนาอัปเดต dependency → โค้ดทำงาน
          มัลแวร์ QUIETVAULT เก็บ API key ของ GitHub และ NPM
          ↳ "using AI that assisted with identifying files of interest"   ← จุดเดียวที่ AI เข้ามาเกี่ยว
          อัปโหลด key ขึ้น GitHub repository สาธารณะ

วันที่ 3   ผู้โจมตีใช้ key ที่ขโมยมาเข้า GitHub และสำรวจสภาพแวดล้อม
          อาศัยความสัมพันธ์ความเชื่อถือ OIDC ระหว่าง GitHub กับ AWS
          ↳ สร้าง AWS STS token ชั่วคราวของ role ชื่อ Github-Actions-CloudFormation

วันที่ 4   "The compromised Github-Actions-CloudFormation role was overly permissive."
          ใช้สิทธิ์นั้น deploy CloudFormation stack ที่มีจุดประสงค์เดียว —
          สร้าง IAM role ใหม่แล้วแนบนโยบาย AdministratorAccess
          ดึงข้อมูลออกจาก S3 · ทำลาย EC2 และ RDS ที่ใช้งานจริง · ถอดรหัส application key
```

**ไม่มี zero-day ไม่มีเทคนิคใหม่** AI ทำงานเพียงขั้นตอนเดียวตรงกลาง — ขั้นตอนที่เมื่อก่อนมนุษย์ต้องทำเอง

ประโยคที่สำคัญที่สุดต่อสิ่งที่จะทำต่อ คือประโยคที่ Google เขียนไว้ตรง ๆ ว่า **role นั้นมีสิทธิ์มากเกินไป**

## การทดลองที่เสนอ

### คำถามวิจัย

> **ขอบเขตของสิทธิ์ IAM ส่งผลต่อ blast radius ของ cloud identity ที่ถูกยึดอย่างไร**

คำถามนี้จงใจ**ไม่ใช่** "least privilege ได้ผลไหม" เพราะคำถามนั้นรู้คำตอบอยู่แล้วและไม่ก่อให้เกิดข้อมูลใด ๆ ส่วนคำถามนี้ให้ตัวเลขออกมา

### วิธีการ

identity ที่ถูกยึด 1 ตัว · ชุด action ตายตัว **15 คำสั่ง** ครอบคลุมการอ่าน เขียน ทำลาย และยกระดับสิทธิ์ · นโยบาย IAM 3 ระดับ ไม่มีตัวแปรอื่นเปลี่ยนนอกจากนโยบาย

| | Policy A | Policy B | Policy C |
|---|---|---|---|
| | สิทธิ์กว้างเกินไป | ปานกลาง | least privilege |
| จำนวน action ที่ทำสำเร็จ | ? / 15 | ? / 15 | ? / 15 |
| จำนวน resource ที่เข้าถึงได้ | ? | ? | ? |

| ยกระดับเป็น administrator ได้หรือไม่ | ได้ / ไม่ได้ | ได้ / ไม่ได้ | ได้ / ไม่ได้ |

**ช่องเหล่านี้ว่างโดยตั้งใจ — การเติมมันให้เต็มคือตัวงาน**

### ทำไม CloudTrail จึงเป็นเครื่องมือวัด ไม่ใช่ของประดับ

ทุก API call ถูกบันทึกพร้อม `eventName` และ `errorCode` การนับบรรทัด log เหล่านั้นคือสิ่งที่เปลี่ยน *"ผู้โจมตีทำอะไรได้บ้าง"* จากความเห็น ให้กลายเป็นการวัดผล

```
policy A   eventName TerminateInstances   errorCode —              → นับเป็นทำสำเร็จ
policy B   eventName TerminateInstances   errorCode AccessDenied   → นับเป็นถูกบล็อก
policy C   eventName CreateRole           errorCode AccessDenied   → นับเป็นถูกบล็อก
```

ถ้าไม่มี log ก็ไม่มีการทดลอง มีแต่การสาธิต

### ขอบเขต

**MVP:** IAM policies · S3 + EC2 · ชุด action ตายตัว · การวัดผลด้วย CloudTrail

**ระยะต่อไป:** OIDC trust · CI/CD identity · การตรวจจับอัตโนมัติ · การตอบสนองอัตโนมัติ
